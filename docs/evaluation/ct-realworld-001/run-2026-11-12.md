## Phase-level performance investigation

The clean Zod profile on code SHA `a4c52e08fd32ba05bb8139bdd25c34ca4152c73d`
attributes 14.3–15.8 seconds to `extractionMs` in its four largest contexts.
Their compiler time was 780–909 ms and fact validation was 1.2–1.7 seconds.
Each Zod package context contained the same 334 admitted files and 48,738 call
observations. This is aggregate candidate evidence; the profile does not split
semantic diagnostics from the other extraction work.

A temporary phase probe from a separate run at SHA
`1cad445ea9d3bd5a2787d16952d37abe230fab26` attributed 14.1–15.7 seconds in
those four large contexts to `program.getSemanticDiagnostics(file)`. Its profile
records `workingTreeClean: false`, so this is diagnostic attribution only and
not a candidate timing result. The probe points to a likely dominant operation,
but does not establish a speedup opportunity.

The owning extractor collects semantic diagnostics for every admitted source
file, then uses overlapping diagnostics to guard call-site, target-declaration,
import-binding and method-reference resolution. The architecture requires a
direct call affected by a compiler error to remain non-exact. Skipping diagnostics
or collecting them only for selected files would also change surfaced compiler
diagnostics and coverage. No such behavior change or optimization was made; the
current evidence does not justify one. Reusing analysis across distinct project
contexts was not attempted because their compiler and resolution inputs define
separate snapshots.

The 110.6-second clean candidate run remains the only profile at `a4c52e0`; it
leaves about 9.4 seconds under the 120-second session deadline. Earlier runs
include a clean 119.9-second completion and timed-out attempts. The phase probe
and these single-run observations do not demonstrate stable deadline headroom.
No performance improvement is claimed.
